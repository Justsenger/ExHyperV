# ExHyperV.WinUI3

使用 WinUI 3 重建 ExHyperV 桌面界面。WPF 版本继续保留，既是可用的产品，也是迁移期间的功能验收基准。两者独立启动，共用 Core，不互相引用。

## 当前范围

主窗口使用延伸内容区的标题栏、Mica 背景及系统窗口按钮，按需导航、浅色／深色／跟随系统主题，以及通过 Core 读取的虚拟机列表。虚拟机页沿用 WPF 的紧凑列表、状态灯、固定顶部概览和独立滚动的资源卡片。列表支持名称和 GUID 搜索；选中后读取配置摘要、基本会话缩略图、逐核心 CPU、内存与 GPU 引擎监控、存储与网卡详情。监控仅在页面可见时顺序采样，不重叠请求；切换对象时取消旧查询，缺测不生成虚假零值。

宿主页展示真实的操作系统、处理器、系统架构和物理内存信息。虚拟机页已接入启动、恢复、正常关机及更多电源菜单；强制断电须明确选择并确认，正常关机失败不会自动升级。创建／导入／删除、导出和控制台尚未迁移，界面不放置这些功能的占位入口。

虚拟机页面分为“状态／设置”。状态页中的处理器、内存卡片共用详情区；显卡、存储、网络使用同一套短下划线页签，选中时显示淡底和主题色短线，切换没有动画。设备卡片支持多行排列与名称中间省略。存储与网络分别显示两个方向的速率图；MAC、IPv4、IPv6 可点击复制，额外 IPv6 地址按需展开。处理器与内存共用相同高度的详情区域，随 CPU 图表排布统一调整。

处理器（含亲和性）、内存、存储、显卡、网络及引导、安全、高级、PCIe 设置已接入 Core，通过设置页左侧分类直接切换。处理器、内存的长表单只布局可见分区；配置状态直接通过 Core 的配置查询读取，不附带控制台可用性检查。时空暂不展示。存储包含添加／更换／移除介质与新建磁盘、ISO；GPU 部署直接消费 Core 的状态、确认请求和清理结果。设置页属于“已实现待完整操作验收”：构建和只读检查不能代替真实修改、部署及失败恢复验证。当前 GPU 监控接口提供 VM 汇总，因此仅单张 GPU 时将读数关联到该设备，多张时明确说明尚不能区分，不复制汇总读数充当逐卡数据。

ARM64 已实际检查处理器、亲和性、内存、存储、GPU 选择和网络页面的读取、返回及文件选择器。未执行虚拟机配置写入或 GPU 部署。列表刷新保留同一虚拟机的页面对象；离页等待期间的操作失败会保留设置页并显示原因。

处理器设置按计算资源、指令集能力、中断控制、处理器拓扑、性能监控、频率调节、寻址与分页、安全隔离分成八个页签，空间不足时自动换行。每次只显示当前分区，编辑值在切换页签时保留。说明收进可悬停或点击的 `i`，不可修改的原因也可从这里查看。CPU 绑定使用独立页面，按宿主实际逻辑处理器编号排列核心格子，支持点击及鼠标拖动选择；全部取消选择后应用表示解除绑定。

应用设置支持浅色／深色／跟随系统，以及默认蓝色、常用色、自定义颜色和关闭主题色。自定义选色采用 WinUI `ColorPicker`，点击“应用”才保存；关闭后保留原选色，选中卡片改用灰色。设置独立保存在当前用户本地应用数据的 `ExHyperV/WinUI3/appearance.json`，重启后恢复，不修改 Windows 或 WPF 的设置。

启动时不读取全量宿主信息、不预热所有页面、不启动 ARP／USB 等后台能力。进入虚拟机页后才查询列表需要的字段。

## 项目边界

```text
ExHyperV.Wpf ──────┐
                  ├── ExHyperV.Core ── 虚拟化引擎、设备与通信后端
ExHyperV.WinUI3 ───┘
```

- Core 负责业务判断、原生调用、资源归属和长流程状态机。
- WinUI 负责窗口、导航、输入、显示、确认对话框和界面状态。
- ViewModel 直接组合 Core 的公开接口。先不增加一套转发所有 Core 方法的服务层、接口层或全局运行会话。
- WPF 的布局、操作顺序、文案和行为可作参考；不直接复用 WPF 控件、窗口类型或 ViewModel。
- 定制 Wpf.Ui 留在 WPF 项目。WinUI 使用原生控件；只有原生控件不能满足实际需求时才增加局部定制。
- WPF 与 WinUI 的窗口状态、外观等客户端设置分别保存。Core 管理的虚拟机元数据仍由 Core 读写。

## 目录与命名

```text
ExHyperV.WinUI3/
├─ App.xaml / App.xaml.cs          应用入口
├─ app.manifest                   管理员启动、DPI 与系统声明
├─ Assets/
│  └─ Styles.xaml                 主题资源与少量共用样式
└─ UI/
   ├─ Shell/                     主窗口与顶层导航
   └─ Pages/
      ├─ VirtualMachines/        虚拟机页面、页面模型、列表项
      ├─ Host/                   宿主信息
      └─ Settings/               客户端设置
```

页面使用 `XxxPage.xaml`，页面模型使用 `XxxPageViewModel.cs`；窗口使用 `XxxWindow.xaml`。页面专用的模型、组件、转换器放在所属页面目录。仅在确实复用时移入 `UI/Shared`，不为对齐 Core 建立 Models／Services／Tools 空目录。

迁移虚拟机设置时，每个子页面拥有自己的编辑状态，如处理器页、内存页、存储页。选中的虚拟机身份由外层页面传入，避免再次形成一个负责所有功能的巨型 ViewModel。

## 界面建议

侧边栏只保留虚拟机、宿主，应用设置固定在底部。默认进入虚拟机；宿主资源在宿主页内组织，不再单独占用顶层导航。

1. **虚拟机页**继续采用左侧列表、右侧详情。详情上方放名称、运行状态和常用操作；配置以子页面组织。不要把 Core 的字段目录直接铺成表单。
2. **配置编辑**显示当前值与待提交值，只提交用户修改的字段。操作完成按实际结果刷新，保留部分失败和需清理状态。
3. **控制台**作为独立窗口。先实现画面、键鼠、尺寸变化与剪贴板；显示适配独立于窗口按钮和菜单。
4. **长流程**以步骤、当前状态、必要确认和实际结果为中心。GPU 部署、导入等直接消费 Core 的状态机，不在界面重写规则。
5. **样式**使用 WinUI 原生导航、表单、菜单和对话框，统一间距与信息密度。浅／深色用主题资源；先保证可读性与键盘操作，再加材质和动效。
6. **性能**首屏先出现，按页面请求字段。性能采样按可见范围订阅；缺测保留上次有效值。视频更新不经普通属性通知逐帧传大数组。

## 迁移顺序与验收

| 阶段 | 实现范围 | 进入下一阶段前的检查 |
| --- | --- | --- |
| 0：框架 | 启动、导航、主题、Core 引用、只读列表 | ARM64／x64 构建；首屏、导航、查询失败、取消和退出 |
| 1：关键路径 | 虚拟机列表与预览、独立控制台窗口、基本／增强会话 | 同一 VM、分辨率和负载，与 WPF 对照画面、输入、剪贴板、刷新节奏、DPI 和资源释放 |
| 2：日常管理 | 电源、创建／导入、处理器、内存、存储、网络、检查点、导出与删除 | 核对实际 VM 状态、修改字段、失败反馈和危险操作确认；不以按钮能点为通过 |
| 3：宿主与设备 | 宿主设置、交换机、GPU／PCIe 配置与部署 | 逐流程对照 WPF，覆盖暂停等待决定、失败和清理；冻结功能不趁迁移扩展 |
| 4：交付 | 托盘、多窗口、快捷键、国际化、设置持久化、签名与分发 | 长时间运行、退出释放、不同 DPI、主题、键盘操作、升级与回退 |

第 1 阶段应尽早完成。控制台显示效率、原生窗口和输入焦点若不能达到要求，先解决这些问题，再投入大量配置页迁移；WinUI 本身不保证比 WPF 更快。

验收时两套界面使用同一版 Core、相同虚拟机和相同测试条件。普通只读页面可以并排比较；会修改同一资源的操作顺序执行。每个功能记录“未迁移／已实现待验收／已验收”，WPF 在整体替换验收完成前不删除。

## 构建与运行

使用 .NET 10、Windows SDK 10.0.26100 和 Visual Studio 的 MSBuild。项目引用 Windows App SDK 2.6.5 稳定版；当前声明的最低 Windows 版本为 10.0.19041，其他系统组合仍需实机验证。

在 Visual Studio 开发者命令行，从仓库根目录执行：

```powershell
msbuild src/ExHyperV.WinUI3/ExHyperV.WinUI3.csproj /restore /t:Build /p:Configuration=Debug /p:Platform=ARM64
msbuild src/ExHyperV.WinUI3/ExHyperV.WinUI3.csproj /restore /t:Build /p:Configuration=Debug /p:Platform=x64
```

Core 含 COM 引用，因此构建完整项目使用 Visual Studio MSBuild。解决方案已列出 WPF 和 WinUI；将 WinUI 项目设为启动项目，选对应架构。Any CPU 配置下 WinUI 映射为 x64；ARM64 使用专用配置，不提供 x86 版本。

输出位于 `bin/<架构>/Debug/net10.0-windows10.0.26100.0/win-<架构>/ExHyperV.WinUI3.exe`。以管理员权限运行，保留同目录所有依赖。Windows App SDK 与 .NET 均采用自包含文件夹部署；当前不是单文件 EXE，也不需要安装 MSIX。正式发布方式在交付阶段确定。

技术依据：[Windows App SDK 稳定通道](https://learn.microsoft.com/windows/apps/windows-app-sdk/release-channels)、[自包含部署](https://learn.microsoft.com/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps)。

## 可选产品组合

`ProductIntegrationTargets` 是显式的构建期导入点。外部产品可通过该 targets 链入 `App.ConfigureProduct` 的 partial 实现，提供 `ProductConfiguration`、`IDesktopWindowProvider` 和可选的 `Pages`。普通构建不设置此属性，不加载外部模块，也不显示产品页面。原有 Core 管理 API 和页面保持共用；当前连接入口由产品自己的页面承载，虚拟机管理页不添加产品专用按钮。

`ProductPageDefinition` 提供标识、标题、图标和页面工厂；产品入口追加在宿主导航之后。页面首次访问时创建，导航切换保留实例；`ProductPageContext.OwnerWindowId` 用于归属文件选择器等窗口。需要后台工作回收的页面实现 `IProductPageLifetime`：正常关闭先等待 `StopAsync` 再 `Dispose`，程序直接关闭窗口时由 `Closed` 补做 `Dispose`。失败后保留窗口的页面必须允许再次操作和重试清理。页面的实际业务留在产品侧，开源壳不引用其类型或本地 DLL。

窗口提供者负责打开、重复打开和关闭所属桌面；所有调用在 WinUI 主线程。主壳关闭时调用 `CloseAll`，回收失败则保留主壳并显示错误。此组合点不是稳定的二进制插件 ABI，更新上游后需要重新构建验证。

`IDesktopWindowProvider` 只表示桌面窗口能力，不等于 `IConsoleConnection` 或可消费的图像/音频流。产品不能仅因能够打开窗口，就把 Core 中尚未实现的 Nimue 帧后端标记为可用。授权校验与商业实现应由外部产品负责。
